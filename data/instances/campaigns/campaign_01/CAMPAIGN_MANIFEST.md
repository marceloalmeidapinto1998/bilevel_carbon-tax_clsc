# campaign_01: materialized instances

This directory holds the actual solver inputs for the computational campaign behind the paper —
every JSON file here is a complete, ready-to-solve problem instance. If you're looking for *why*
each experiment exists, read
[`experiments/campaign_01/EXPERIMENTS.md`](../../../../experiments/campaign_01/EXPERIMENTS.md) first;
this file explains what you'll find if you open the files themselves.

## What's in one instance file

Every file here is a JSON document with four top-level keys:

- **`name`** — the instance's identifier, e.g. `STD_I17_M4_T3__exp3_rho_50`.
- **`metadata`** — provenance and units: which base instance this was derived from, the campaign
  bookkeeping (see below), physical unit conventions, and a `generated_at_utc` timestamp.
- **`sets`** — the index sets of the model: `S` suppliers, `F` factories, `W` warehouses,
  `R` retailers, `AIR`/`PORT` transport hubs, `P` products, `U` raw materials, `G`/`L` production
  and remanufacturing technologies, `T` planning periods, and several derived sets (arcs,
  product-technology pairs, transport-mode families).
- **`parameters`** — every numeric input the model needs: costs, capacities, emission
  intensities, demand, distances, and so on (about 70-80 parameter tables per instance).

Every campaign instance additionally carries a `metadata.campaign` block recording exactly how it
was produced:

```json
"campaign": {
  "campaign_id": "campaign_01",
  "experiment_id": "exp3",
  "design_point_id": "exp3-rho-50",
  "base_instance_id": "STD_I17_M4_T3"
}
```

That means every file here is fully reproducible from three things: the **base instance** it
started from (`data/instances/base/<base_instance_id>.json`, generated by
`clsc.generator`), the **design point** that describes what was changed
(`experiments/campaign_01/<exp>/design_matrix.csv`, row `design_point_id`), and the
**materialization code** that applies that change (`clsc.campaign.instances.materialize`). Nothing
here is hand-edited.

## Directory convention

```
<exp>/<cell>/<run_code>.json
```

- **`<exp>`** is one of `exp1`, `exp2`, `exp3`, `exp4`.
- **`<cell>`** is the structural test instance this file is based on: `STD_I<n>_M<m>_T<t>` for
  `n` supply-chain nodes, `m` a materials/products richness code, `t` planning periods — or one of
  the six tiny `STD_TOYn` instances used only by `exp1`.
- **`<run_code>`** identifies *what was done* to that cell for this particular run. Its meaning is
  specific to each experiment — see below.

## What each cell represents

A cell's name encodes three sizing choices, each a deliberate step up in difficulty:

- **`I<n>`** — the number of supply-chain nodes (suppliers + factories + warehouses + retailers +
  transport hubs combined): **17** or **25**.
- **`M<m>`** — a materials/products richness code, *not* a literal count: `raw_materials = m // 2`,
  `products = m // 4`, so **`M4`** means 2 raw materials and 1 product, **`M8`** means 4 raw
  materials and 2 products. (Two cells, described below, go further: `M12` — 6 raw materials, 3
  products — and `M16` — 8 raw materials, 4 products.)
- **`T<t>`** — the number of planning periods: **3**, **6**, or **12**.

Crossing the two `I` values, the two `M` values, and the three `T` values gives the campaign's
**12 core structural cells** — not a statistical design, but 12 genuinely different optimization
problems (more periods means more decision variables and a longer planning horizon; more
materials/products means a denser bill-of-materials and more technology choices). Six of them are
markedly harder to solve than the other six and get correspondingly longer time limits
(`clsc.campaign.designs._cells`, `STANDARD_TIER_CELLS` vs. `HARD_TIER_CELLS`):

| | `T3` | `T6` | `T12` |
|---|---|---|---|
| **`I17_M4`** | standard | standard | *hard* |
| **`I17_M8`** | standard | *hard* | *hard* |
| **`I25_M4`** | standard | standard | *hard* |
| **`I25_M8`** | standard | *hard* | *hard* |

Each period spans 17.33 weeks, so `T3`/`T6`/`T12` correspond to roughly one, two, and four years of
planning horizon. Every `T12` cell is hard-tier — four years of periods is simply a bigger
problem — and so are the two `M8_T6` cells: `STD_I17_M8_T6` was promoted into the hard tier after
an earlier run
stagnated at a 6.2% optimality gap under the standard tier's time limit, so it now shares the
longer budget with `STD_I25_M8_T6`.

Experiments 2 and 3 don't run every cell — solving all 12 at full cost, for every ablation variant
and policy rule, would multiply the campaign's runtime for little extra insight. Instead each draws
from its own fixed subset of cells; the exact `cell × run_code` coverage is laid out as a table in
each experiment's own section below.

A few more cells exist outside the 12-cell grid, each for one narrow purpose:

- **`STD_I25_M12_T6`**, **`STD_I25_M16_T6`** — `exp2`'s materials/products-richness escalation
  probes: richer than any of the 12 core cells (M12: 6 raw materials/3 products; M16: 8 raw
  materials/4 products), at fixed I25-T6, extending the M4→M8 axis one and two steps further.
- **`STD_I33_M8_T6`** — `exp2`'s node-count escalation probe: more supply-chain nodes than any of
  the 12 core cells (`entity_split(33)`), at fixed M8-T6, extending the I17→I25 axis one step
  further.
- **`STD_TOY1`** … **`STD_TOY6`** — six deliberately tiny instances (1-2 products, 1-2 periods, one
  node per echelon) built only for `exp1`, small enough that a reader can re-derive the optimal
  network by hand and check the solver against it.

All three escalation bases are generated by `clsc.generator.build_escalation_specs`/
`generate_escalation_bases` — deliberately kept separate from `python -m clsc.generator benchmark`
so they never silently appear in the standard 12.

## exp1 — verification

| `run_code` pattern | What it is |
|---|---|
| `toy_STD_TOYn.json` | One of six tiny, hand-verifiable instances (1-2 products, 1-2 periods, one node per echelon). |
| `base.json` | The unmodified structural cell, solved once to check the solver reaches a certified-exact optimum. |
| `invariant_tau0000.json`, `invariant_tau2000.json` | The same cell at a fixed carbon-tax index (0 and the grid ceiling), used to check that a direct fixed-tax solve agrees with what the full bilevel run reports at that same tax. |
| `seedprobe_s1.json`, `seedprobe_s2.json` | The same cell again, only the solver's internal random seed changes — checks that the certified answer doesn't depend on it. |

## exp2 — computational performance

| `run_code` pattern | What it is |
|---|---|
| `M0_seed0.json`, `M0_seed1.json` | The cell solved with the full, unmodified algorithm ("M0"); `seed1` is a second run with a different solver seed, to gauge run-to-run noise. |
| `A1.json` | Same cell, with the algorithm's in-loop minimum-tax confirmation step disabled. |
| `A5.json` | Same cell, with the algorithm's incumbent-bound cut disabled. |

`M0_seed0` is the one run_code every cell gets — it's the full-method reference every other column

`A1`/`A5` need cells spanning easy-to-hard to show the effect holds generally; the seed check
and the three `escalation_*` cells each need only their own one cell.

## exp3 — policy value & calibration

| `run_code` pattern | What it is |
|---|---|
| `P0_no_tax.json` | The cell at zero carbon tax — the "do nothing" policy rule. |
| `P1_ceiling.json` | The cell at the highest tax the grid allows — the "maximally aggressive" policy rule. |
| `P2_mid.json` | The cell at a tax halfway up the grid — a naive "moderate" policy rule. |
| `rho_1.json` … `rho_200.json` | The same cell solved in full (leader + follower together) at a different assumed price for one tonne of emissions — this sweep is how the campaign settles on a defensible price. |

| cell | `P0_no_tax` | `P1_ceiling` | `P2_mid` | `rho_*` sweep |
|---|---|---|---|---|
| `STD_I17_M4_T3` | ✓ | ✓ | ✓ | ✓ (5 runs) |
| `STD_I17_M8_T6` | ✓ | ✓ | ✓ | |
| `STD_I25_M8_T6` | ✓ | ✓ | ✓ | |
| `STD_I25_M8_T12` | ✓ | ✓ | ✓ | |

The three policy rules run on all four cells this experiment covers, so the comparison against the
algorithm's own chosen tax (read from `exp2`'s results, not re-solved here) holds up across the
size range. The `rho_*` sweep only runs on `STD_I17_M4_T3` — it's a single-cell calibration
question (what price makes the tax defensible), not a claim that needs to generalize across cells.

Two further kinds of file belong here but don't exist until earlier results do: a handful of
`refine_below_*`/`refine_above_*` fixed-tax probes near the algorithm's chosen tax (need `exp2`'s
results first), and an `anchor_*`/`frontier_*`/`eps_anchor_*` set at the price the `rho_*` sweep
settles on (needs that sweep solved first). Their absence isn't a gap — they're generated
automatically once those results land.

## exp4 — sensitivity

Every file here sits under `STD_I17_M4_T3` — this experiment deliberately runs on one cell only,
since it's asking a question about the *model's inputs*, not about how the answer changes with
instance size.

Every `cont_r*.json` file scales the same eight factors from their baseline (multiplier 1.0) to
either a **low** or a **high** multiplier — never both up or both down for every factor at once,
which is the point of a fractional factorial design: 32 carefully chosen combinations, instead of
2⁸ = 256, are enough to estimate each factor's effect on cost and emissions.

| factor | what it scales | low | high |
|---|---|---|---|
| `dem` demand | retailer demand | ×0.7 | ×1.3 |
| `ret` return availability | return/collection rate | ×0.5 | ×1.5 |
| `cap` capacity | production & remanufacturing capacity | ×0.7 | ×1.3 |
| `emi` emission intensity | production & remanufacturing emissions | ×0.5 | ×1.5 |
| `sc3` scope-3 emissions | supplier (raw-material) emission intensity | ×0.5 | ×1.5 |
| `trn` transport emissions | shipping emission intensity | ×0.5 | ×1.5 |
| `rec` return economics | recovered-item acquisition cost | ×0.5 | ×1.5 |

## Reproducing or regenerating this directory

Nothing here needs to be committed to be trusted — it's cheap to regenerate:

```bash
python -m clsc.campaign.orchestrator generate --experiment all   # (re)build design_matrix.csv
python -m clsc.campaign.orchestrator run --experiment <1..4|all> # materialize + solve
```

`run` materializes each design point's instance immediately before solving it, so this directory
is naturally kept in sync with `experiments/campaign_01/*/design_matrix.csv`; deleting the whole
directory and re-running loses no information, since every file is a deterministic function of the
base instance plus its design point.
